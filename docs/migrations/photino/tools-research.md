# Windows Photino tools research

## Entry state
Branch photino-05-tools starts from initial UI checkpoint e1602a7. The checkpoint passed a Visual Studio solution build and 81 tests. Task 04 remains incomplete; this branch can carry follow-up UI workflows as well as task 05 utilities. No implementation in this document is claimed delivered.

## Existing implementation boundaries
- `TM/Services/SecurityToolsService.cs` orchestrates base64, file encryption with document/password/current-account keys, certificates, signatures, public-key encryption, purge, hashes and HMAC. It depends on WPF interaction and shell services, so it cannot be injected into the Photino host unchanged.
- `TM/Helpers/FileHelper.cs` combines file-dialog helpers with encryption overloads. Preserve existing formats and Windows-account semantics when separating these operations.
- `TM/Helpers/HashHelper.cs` supports MD5/SHA1/SHA256/SHA384/SHA512 file hashes and HMAC sidecars. `SecurityToolsService.CreateHmac` appends a Base64 salt; derivation uses context `HMAC` and length 64. Existing tests are `HashHelperTests.cs` and `FileHelperTests.cs`.
- `TM.Core/Services/ProjectCryptoService.cs` already owns secret encryption, password changes, private-key access, signing, certificate/key stores and encrypted document serialization. Retain its existing algorithms and DPAPI handling.
- `TM/Services/ProjectDocumentService.cs` implements the legacy `.sav` transfer format: exported XML is GCM-encrypted under a random key and Base64 encoded. Despite legacy 'unencrypted' naming, this is not a plaintext file. Import requires a transfer key and a new document password. Preserve format compatibility and add bounded parsing/atomic output rather than copying legacy file handling verbatim.
- `TM/Helpers/ClipBoardHelper.cs` uses WPF Clipboard and DispatcherTimer. Its unconditional delayed clear is unsuitable as the new adapter contract: expiry should only clear a still-owned clipboard value, not unrelated clipboard content copied later.
- `TM/Models/MainWindowViewModel.cs` has the existing generated-password command and protected-value editor flow.

## Proposed implementation slices
1. Generated protected passwords through the existing serialized workspace gate, bounded validated length, explicit replacement confirmation, dirty/revision updates, no plaintext in retained snapshots and HTTP tests. This is the smallest first slice and requires no new filesystem API.
2. Document password change with old/new/confirmation inputs, atomic failure behavior, empty/no-protected-item support, save/reopen compatibility and wrong-password tests. Current `ChangeMasterPassword` returns false for empty documents or documents without protected items; direct exposure would preserve that gap.
3. Native clipboard interface with Windows UI-thread dispatch, ownership-aware expiry, replacement/lock cleanup and fake-based tests before native acceptance.
4. Dialog-free file utilities plus native dialog contracts, starting with non-destructive hashes/base64. Add encryption/HMAC/signature/certificate adapters in individually tested slices. Never trust browser-supplied paths; guard overwrites, cancellation and partial output.
5. Legacy transfer import/export through bounded parsing, transient key presentation, native paths and frozen compatibility fixtures.

## Security and validation gates
All document/key operations must remain serialized with workspace lock/replacement. Razor handlers validate and delegate; they must not manipulate documents or native controls. Keep sensitive inputs out of persisted view models, logs and error messages. Zero temporary byte buffers in finally blocks. MD5/SHA1 are legacy compatibility options, not modern security recommendations. File purge needs explicit destructive confirmation and must not promise secure erasure on SSDs.

Each slice requires service and HTTP coverage, Visual Studio solution build/tests, and documented native/manual gaps before its checkpoint. Keep WPF runnable. Windows DPAPI and jnUtil stay in place; Linux/macOS and stable tagging are deferred.

## Generated-password slice design
- Reuse `SecurityHelper.GeneratePassword(length, complex)` as in `MainWindowViewModel.GeneratePassword`; match the WPF slider's 5–30 bounds and default length 12, with complex mode opt-in. These are compatibility settings, not a recommendation for short passwords.
- Append a GeneratePassword action to the command enum, plus validated length, complex-mode and dedicated replacement-confirmation fields. Keep existing enum values stable.
- Validate revision, unlocked document, target type and confirmation before generating. Encrypt into a local value before assigning the node; update selection, dirty state and revision only on success.
- Return no plaintext on generation. Use the existing explicit reveal flow to view the result. Dispose the generated SecureString and call the existing ZeroString helper on the temporary plaintext in finally; do not claim guaranteed managed-memory erasure.
- A separate form must state that generation replaces the protected password immediately in the document and still requires saving. It must not silently apply unrelated editor fields; existing unapplied-edit confirmation remains active.
- Cover minimum/default/maximum lengths and both modes, encrypted save/reopen, unchanged non-secret fields, stale revisions, missing confirmation, invalid lengths, wrong/missing targets, cancellation and locked/no-document states. HTTP tests must prove that generation and ordinary GETs do not reveal plaintext, malformed input is rejected without mutation, and lock removes reveal state.

## Document password-change slice design
- `ChangeMasterPassword` previously authenticated only indirectly by decrypting entries and returned false when no entries existed. Authenticate the derived old key against the active DPAPI-unprotected master key using fixed-time comparison, even for empty documents.
- `GetProjects()` creates detached entities. Re-encrypt these, materialize replacement nodes, and prepare DPAPI protection before replacing the live key/nodes. Wrong passwords, corrupted entries and staging failures must leave active salt/key/nodes untouched. Keep ECDH keys and certificate state unchanged.
- Re-encryption should retain plaintext as a temporary byte buffer rather than a string, and clear both derived keys and plaintext in finally. Password input disposal must cover derivation failures too.
- Add bounded new-password and confirmation fields; require a nonempty new password, equality and explicit acknowledgement. Execute under the workspace revision gate; success marks dirty, preserves selected ID and never returns passwords. Razor clears new sensitive inputs and ModelState alongside existing password inputs.
- Changing the master password rotates the document-derived keys (legacy behavior). Warn that previously encrypted files/HMACs using that document key require the old document/key; saving replaces the current file's password, while discard restores its previous saved state. Do not claim the operation rekeys external files.
- Validate empty/no-protected/populated documents, old-password rejection, corrupted-later-entry rollback, preserved key/certificate fixture compatibility, save/lock/new-password reopen, dirty/discard/stale/cancellation/locked guards and HTTP non-disclosure. Native form acceptance remains separate.
- Validation exposed an empty-document old-password acceptance on reopen. The reader now requires a decrypted `projects` element and no remaining XML `EncryptedData`; deterministic missing-payload coverage complements wrong-password round trips. This preserves the legacy format, not a claim that the CBC envelope is authenticated.

## Clipboard slice design
- Use a Windows native adapter on a dedicated STA thread with a hidden message-only window and message pumping; no WPF/WinForms reference or browser clipboard permission is needed. Native clipboard ownership must outlive the write.
- Serialize backend work and track the native sequence number plus owner window. Check ownership and clear while OpenClipboard is held, so a later external copy (even identical text) is not erased. Never read clipboard contents to compare secrets.
- Put Unicode text in movable native memory, transfer ownership only after SetClipboardData succeeds, and zero/free allocations on failure. Mark content excluded from Windows history/cloud processing on a best-effort basis; do not claim other applications cannot read it.
- The expiring service stores only sequence/timestamp metadata, uses TimeProvider and a 15-second default, and serializes copy/expiry/clear. A hosted loop retries busy clipboard cleanup once per second. Lock, successful document replacement and shutdown request owned cleanup; busy failures stay pending without blocking document locking. Crashes and contention can prevent or delay cleanup.
- Copy is a protected-item-only workspace command under the existing revision gate. Decrypt transiently, send directly to the native service, clear the temporary string, and return no plaintext to Razor. Guard against embedded NUL truncation.
- Tests use a fake native boundary, never the user's clipboard: expiry, repeated copies, external replacement including identical text, busy retries, copy failure, shutdown and workspace/HTTP non-disclosure. Real Windows copy/paste, history/cloud behavior and native shutdown remain manual acceptance.

## File hashing/Base64 slice design
- `HashHelper` writes uppercase hexadecimal grouped every four bytes with a trailing space; preserve that text format. Default SHA-256 and allow only MD5/SHA1/SHA256/SHA384/SHA512, labeling MD5/SHA1 legacy. No HMAC or document key access in this slice.
- Separate native input/output file selection from `TM.Core` streaming transformations. Browser commands contain only an operation enum, never paths, output names or file contents. A dedicated tools page avoids replacing unsaved document editors; results/errors are generic and do not disclose paths.
- Read source with FileShare.Read and publish a closed temporary output in the destination directory with no-overwrite File.Move. Reject identical paths and existing destinations, including destination races at publication. Never alter/delete the source or a preexisting destination. Clean up only a temporary file actually created by this operation.
- Stream hash and Base64 with bounded buffers and cancellation; decode accepts ASCII Base64 whitespace and UTF-8 BOM, rejects malformed/truncated/trailing data after padding. Clear managed transformation buffers in finally. Base64 is not encryption, and temporary-file deletion is not secure erasure.
- Extend the Photino dialog adapter with a distinct file-tool contract and share the attached instance in production. Serialize tool operations and retain the gate until a native dialog resolves even if its request was canceled, avoiding an abandoned dialog launching a later operation.
- Cover standard/legacy hash text, Base64 sizes across buffer boundaries and jnUtil interoperability, malformed input cleanup, missing input, existing/same destination, cancellation, fake-dialog cancellation, HTTP authentication/antiforgery, enum validation, browser-path injection and non-disclosure. Native selection/progress UX remains manual acceptance.

## Password file-encryption slice design
- WPF `FileHelper.EncryptFile(path, SecureString)` calls `SecurityHelper.AesEncryptFile` then wipes the input. Do not reuse that destructive wrapper. Call the existing password-based jnUtil encrypt/decrypt overloads directly and retain the original input, with an explicit UI warning about retained plaintext.
- Stage in a unique directory beside the destination using a nonexistent payload path (jnUtil rejects precreated outputs), and publish with no-overwrite move only on success. Refuse same/existing output paths. Cleanup deletes only the known payload then the empty directory, covering false results, exceptions and cancellation; deletion is not secure erasure.
- Legacy calls are synchronous: execute via Task.Run and await completion, then check cancellation before publication. Never abandon a still-running operation or dispose its password early. No claim of immediate mid-operation cancellation or a changed/authenticated file format.
- Introduce a separate password-operation enum and form handler, defaulting to encryption, with maximum 4096-character password inputs and matching confirmation for encryption. Validate before native dialogs, share the existing file-tools gate, clear model/password state and render generic status only.
- Verify bidirectional jnUtil compatibility using synthetic disposable files, empty and multi-buffer content, wrong-password/malformed-input failures, source/output preservation and cleanup, pre-cancellation, invalid/oversized/unconfirmed HTTP input, no password/path echo and ignored browser-supplied paths. Native dialog/large-file UX remains manual acceptance; document-key/HMAC/account-bound variants remain deferred.

## Document-key file slice design
- Match `SecurityToolsService.EncryptFile/DecryptFile`: HKDF context `file encryption`, fresh 32-byte salt stored by jnUtil encryption, 32-byte key, and decrypt with the stored 32-byte salt. Do not call destructive WPF FileHelper wrappers.
- Require a saved, clean, unlocked workspace before any native dialogs. This prevents external files being bound to an unsaved/rekeyed document that the user can discard. Keep a recoverable copy of the original document/password; later password changes rotate derived file keys.
- Hold the workspace revision gate for dialogs and the complete awaited operation; nest the shared file-tools gate beneath it (no reverse dependency). Lock/replacement/rekey cannot clear or change keys while the legacy worker runs. No key or arbitrary document callback is exposed to page models.
- Stage/publish with the password-file safety pattern, preserve source, refuse existing output, clear derived-key buffers even if jnUtil replaces the ref parameter. Validate extracted salt length and document key availability before crypto. Cancellation cannot interrupt synchronous legacy calls; await then refuse publication.
- Test bidirectional legacy compatibility, empty/multi-buffer inputs, wrong-document rejection, malformed input cleanup, existing destinations/cancellation, saved/dirty/locked/stale workspace guards, lock serialization and HTTP path/key non-disclosure. HMAC and account-bound file support remain separate slices.

## HMAC slice design
- WPF creates a grouped uppercase hex MAC (space after each four bytes), newline, then Base64 32-byte salt using context `HMAC` and a 64-byte derived key. Preserve this content format for all five existing algorithms; algorithm selection is external to the sidecar. Default SHA-256, label MD5/SHA1 legacy.
- Stream file hashing with cancellation and clear derived keys in finally. Verify with CryptographicOperations.FixedTimeEquals after validating the selected algorithm's digest size. Wrong document, modified data/MAC/salt yields failure rather than a successful verification.
- Bound sidecars to 4096 bytes using a bounded stream read, not only a pre-read file length check. Decode strict UTF-8 (optional BOM), accept LF/CRLF and trailing whitespace, and require exactly two content lines, valid hex and a 32-byte Base64 salt. No paths/algorithms are trusted from sidecar content.
- Stage new sidecars with CreateNew and no-overwrite publication. Verification is read-only. Select the data file then the existing sidecar natively for verification; select a new output natively for creation. Use the saved/clean workspace guard and workspace-then-file-tools gate order.
- HMAC is shared-key integrity, not public signer identity. Keep the original document/password for verification after password changes. Tests cover all legacy algorithms bidirectionally, malformed/oversized inputs, wrong keys and changed data/MAC/salt, output preservation/cancellation and HTTP/workspace guards. Native/large-file acceptance remains pending.

## Windows-account file slice design
- Inspected installed jnUtil 2.0.2 methods with ILSpy: `EncryptFile_Account` and `DecryptFile_Account` call `File.Encrypt` and `File.Decrypt` after a Windows guard. This is Windows EFS, not DPAPI file-blob encryption. WPF then renames the same file with/removes `.enc`; the extension is not a ciphertext format. Do not replace EFS with a different scheme or change document DPAPI.
- Provide an injectable EFS boundary with encrypted-attribute inspection and a Windows implementation retaining those jnUtil calls. Automated tests use a fake; do not create/change the developer's EFS certificates or claim native EFS acceptance.
- Copy the selected source into an operation-created staging directory beside the new output, close the handles, run the synchronous EFS operation off the request thread and await it. Verify the resulting encrypted attribute matches the requested operation before no-overwrite publication. Require an EFS-encrypted source for decryption. Never alter the source or an existing destination; clean only the known payload and empty staging directory.
- Hold the shared file-tool gate through dialogs, copy and protection. Validate the operation and explicit acknowledgement before dialogs. Cancellation during a synchronous EFS call cannot interrupt it; await completion then refuse publication. Source/output paths come only from native dialogs; error/status messages must be generic.
- Clearly label Windows EFS, supported NTFS/Windows edition/policy requirements, EFS certificate/private-key recovery, transparent current-user access and possible protection loss on copying/export. Original plaintext is retained; temporary plaintext cleanup is deletion, not secure erasure. This is not a portable encrypted attachment or Linux/macOS feature.
- Test fake-backed encryption/decryption, empty/multi-buffer copying, same/existing output refusal, invalid/plain source rejection, boundary failure/no-op, destination races, cancellation before/during the native call, cleanup, HTTP authentication/antiforgery/acknowledgement and path non-disclosure. Real EFS round trips, attribute checks after publication, denied-account access, recovery, Unicode paths and unsupported volume/edition behavior remain manual acceptance.

## Public-key file slice design
- WPF `SecurityToolsService.EncryptWithPublicKey`/`DecryptWithPrivateKey` obtains the active document ECDH private key, Base64-decodes a peer SPKI public key, calls `SecurityHelper.DeriveSymmetricKey`, then calls `SecurityHelper.GCMEncrypt`/`GCMDecrypt`. jnUtil's compatible payload is `nonce (12 bytes) || tag (16 bytes) || ciphertext`; there is no filename, sender identity, public-key identifier or associated data in the payload.
- Require a saved, clean, unlocked document with an ECDH key pair before native dialogs. Hold the workspace lifetime gate across peer-key decoding, dialog selection and the full awaited operation, then nest the file-tools gate. Lock, replacement and password changes cannot clear the DPAPI-protected private key while it is used.
- Peer key text is bounded Base64 SPKI input, decoded once by the workspace service, and passed as bytes to a core service. Do not store peer text/bytes in snapshots or return them through Razor; clear decoded peer bytes and derived/private key buffers in finally blocks. The core service does not access UI/document state and validates peer input length before key import.
- Preserve the legacy complete-file GCM payload and therefore retain whole-file memory behavior. Refuse inputs over 64 MiB before allocating; this is an explicit Photino UI limit rather than a format change. Use a staged payload in the output directory and `File.Move(..., overwrite: false)` after crypto/cancellation checks. Source and existing outputs remain untouched; cleanup deletes only the known staged payload and empty staging directory.
- Encryption/decryption share the same ECDH derivation. Decryption requires the sender's public key supplied out of band; this demonstrates a shared secret, not an authenticated sender identity, signature or key trust model. Public keys are not secrets, but accepting an unverified substituted key provides no recipient/authentication assurance.
- Tests use synthetic disposable ECDH pairs and legacy jnUtil calls for bidirectional payload compatibility, empty/multi-buffer files, wrong peer/tamper/malformed payload rejection, invalid peer input, output/source preservation, existing/same output refusal, cancellation and staging cleanup. Cover saved/dirty/locked/no-key/stale workspace guards, locking serialization, session/origin/antiforgery, ignored browser paths and peer/path/content non-disclosure. Native dialogs and real cross-machine key exchange remain manual acceptance.

## CMS signing slice design
- WPF `CreateSignature` calls `ProjectCryptoService.SignFile`, which creates a detached `SignedCms` signature with jnUtil `CMSHelper.Sign(data, certificate, X509IncludeOption.EndCertOnly, "SHA256")`; the `.p7c` file is a CMS/PKCS#7 payload, not an encrypted file. Preserve this payload and default extension without overwriting existing output.
- `EnsureCaCertificate` can generate a document CA certificate and mutates document state. Require a saved, clean, unlocked document before generation; generation marks dirty and increments revision, then requires save before signing. Sign requires a current loaded certificate, document lifetime gate and file-tools gate through native selection and completion. Certificate import/export are separate pending work.
- Signature verification needs no active document/certificate. Select the data file then the detached CMS file using native dialogs. Report cryptographic signature validity separately from system certificate-chain trust: `CheckSignature(true)` establishes mathematical signer validation only; chain building is best-effort, with revocation retrieval disabled to avoid network access. Do not call the ambiguous legacy `CMSHelper.Verify(data, sig)` overload as its chain semantics are inverted/nonstandard.
- Preserve legacy whole-file CMS behavior with a 64 MiB per-input limit before allocation. Stage signatures in an operation-specific directory beside the destination and publish via no-overwrite move only after cancellation checks. Verification is read-only. Source, signature and existing outputs remain unchanged; cleanup deletes only operation-owned payload/staging directory and is not secure erasure.
- Generic UI results/errors omit paths, contents, certificates and exception details. CMS signatures can contain certificate identity material; do not render CMS content. A valid signature alone does not establish a trusted identity, certificate policy, revocation state, timestamp or long-term signature validity.
- Test synthetic document certificates and legacy jnUtil signatures in both directions, empty/multi-buffer data, altered data/signature failures, malformed CMS, existing/same output, cancellation/cleanup and output preservation. Cover saved/dirty/locked/no-certificate/stale workspace guards, lock serialization, native-only file paths, session/origin/antiforgery and non-disclosure. Real certificate trust stores, cross-machine chain trust, revocation, timestamping, import/export and native acceptance remain manual/future work.
